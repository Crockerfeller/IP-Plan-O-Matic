Azure VNet subnet sizing

Azure reserves 5 addresses in every subnet, many services need a subnet of their own with a fixed name or minimum size, and a subnet is hard to resize once it’s in use. Here is how to size them before you build.

Quick answers: a /24 has 251 usable addresses in Azure. The smallest subnet is a /29, with 3 usable. GatewaySubnet should be a /27, AzureBastionSubnet and AzureFirewallSubnet a /26, and Application Gateway v2 a /24. Open the subnet wizard to create them.

The 5 reserved addresses

In a subnet such as 10.1.0.0/24, Azure keeps:

  • 10.1.0.0: the network address
  • 10.1.0.1: the default gateway
  • 10.1.0.2 and 10.1.0.3: map Azure DNS into the VNet
  • 10.1.0.255: the broadcast address (Azure has no broadcast, but reserves it)

The first address you can give a VM is .4. The same 5 are reserved at every size, so small subnets lose the most: a /29 keeps only 3 of its 8.

Size limits

An IPv4 subnet can be anything from a /29 up to a /2. IPv6 subnets in a dual-stack VNet must be exactly a /64. A VNet can have several address spaces, and you can add more later, even while it’s peered.

Ranges you can’t use

Any private range works for a VNet, but Azure refuses 224.0.0.0/4 (multicast), 255.255.255.255/32 (broadcast), 127.0.0.0/8 (loopback), 169.254.0.0/16 (link-local) and 168.63.129.16/32 (the Azure platform’s virtual IP).

Subnets Azure services need

Some services need a subnet with an exact name. Others need a subnet delegated to them, which other resources can’t share. Plan these before you fill the VNet with workloads. Each service links to its Microsoft Learn page.

Create these subnets in the planner. The subnet wizard lists every service below: tick the ones you need, and each gets its own subnet with the required name or delegation, at the recommended size and never below the minimum. You get one VNet with all of them, or switch to hub and spoke to put shared services in a hub, then export it to Terraform.

Sizing an AKS subnet

How many VNet addresses AKS uses depends on its network plugin. Count the most nodes the cluster can scale to, plus the extra nodes an upgrade adds (surge, 1 by default):

  • Azure CNI Overlay (the default for new clusters): only nodes take VNet addresses. Pods get theirs from a separate range, 10.244.0.0/16 by default.
  • Azure CNI on the node subnet (the traditional plugin): each node also reserves one address for every pod it can run, so it takes max pods + 1. Max pods defaults to 30.

For 50 nodes:

PluginAddresses neededSmallest subnetUsable
Azure CNI Overlay50 + 1 = 51/2659
Azure CNI (node subnet)(50 + 1) × (30 + 1) = 1,581/212,043

Either way, the pod range and the Kubernetes service range (10.0.0.0/16 by default) must not overlap the VNet or anything connected to it. If your VNets use 10.0.0.0/16, pick another service range when you create the cluster.

Tips

  • Leave room to grow. Changing a subnet’s range generally means emptying it first, so keep free space in each VNet rather than handing it all out.
  • Connected networks can’t overlap. Peering, VPN and ExpressRoute all need unique ranges, so carve every VNet from one master plan. The planner’s Check & summarize tab tests a plan against your existing networks.
  • Give each region or environment its own block, such as a /16. Routes stay easy to summarize, and each hub and its spokes have a clean boundary.
  • Count IP addresses, not VMs. Load balancers, private endpoints, scale sets and App Service instances use addresses too. See how many hosts are in a subnet.
